# Phase 4：最小记录器与静态基线协议

本文件描述实验方法。三类扰动的正式结果另行汇总，不能把工具实现当作鲁棒性验收。

## 数据流与职责

相机 → 检测器 → 控制器 → 运动命令，仍是原来的控制链。
新增的 `/ibvs/observation` 只负责观测：控制器每次更新绿色特征时，将实际锁存目标、绿色特征、误差一起发送给记录器。它是 JSON 格式的 `std_msgs/String`，只有 `record_observations=true` 才发布。

记录器不把自己收到的第一个红点当成控制器锁存目标，也不依赖被节流的 Holding 日志。进入死区后，绿色特征更新仍产生观测消息。因此记录器能够继续观察是否离开死区。

正式运行时控制器以 `start_paused=true` 启动。记录器先核对生效参数和观测连接，再通过 `/ibvs/start_trial` 请求开始；控制器确认 JTC 与记录器均匹配后，才执行原运动控制循环。手动运行默认不暂停。

控制器另保存第一条运动命令的单调发布时间、关节起点和目标位置，随观测消息重复发送。记录器比较它与自己收到的首条轨迹，记录接收延迟；不匹配或延迟超过 0.5 秒时，该 trial 不进入干净性能比较。曾有无握手的 trial 在收到首条命令时机器人已运动，导致计时偏短；这类记录须保留并单列排除，不能沿用其成功标志。

- `trial_metrics.py`：纯 Python 判定器，不导入 ROS；用人工时间和误差检查规则。
- `run_phase4_trial.py`：启动本轮场景、检测器与控制器；接收消息；保存结果；只关闭自己启动的进程。
- `errors.csv`：接收时刻、相对首条命令时间、真实锁存目标、绿色特征、误差、最新检测红点及观测消息年龄。
- `result.json`：版本、参数、初始化、结论、异常和退出状态。成功和失败都会保存；输出目录已经存在时拒绝覆盖。
- `controller_parameters.yaml` 和各节点日志：本次实际请求的配置及诊断证据。运行器另通过参数服务核对生效值。

`feature_mono` 是控制器处理绿色质心回调时的单调时间，供同一容器内的记录器判断观测消息是否积压；不是相机采集时间。控制器的误差状态在这次回调中更新，运动控制周期仍按原参数运行；并非每条观测都对应一条已执行运动命令。现有 Point 质心消息没有 Header，本协议不测端到端延迟。

## 固定判据

1. 记录器就绪并请求启动场景后，最多等待 30 秒出现第一条轨迹命令。等待就绪不算收敛时间。
2. 第一条轨迹命令的接收单调时间为 t0。此后 30 秒内必须完成连续至少 3 秒的误差严格小于 5 px。
3. 只在新鲜的新样本到达时确认保持成功，不用旧值靠定时器补足三秒。误差等于或超过 5、超过 0.5 秒没有有效样本、观测消息过期或丢失，都会中断当前保持区间。
4. 收敛时间取成功保持区间的起点。例如 t0 后第 4 秒进入，第 7 秒完成保持，则收敛时间为 4 秒。
5. 最终误差是结束前 3 秒内有效样本的均值和最大值，并报告样本数与实际覆盖时间；结束时数据已过期则填 null，不填零。
6. `geometric_converged` 与无异常成功分开。有过期、消息丢失、控制器 stale 警告或时钟异常时，即使后来进入死区，也不会成为无异常成功样本。`controller_stale_warning_count` 是节流后的日志条数，不是逐帧超时次数。
7. 系统时间与单调时间增量差超过 0.25 秒时记为时钟事件。记录器使用单调时间，不改变控制器原有时钟语义或 use_sim_time。

`formal_candidate` 表示可纳入同协议对比的干净版本样本，不代表成功。数据正常但 30 秒内未收敛的 trial 仍是正式失败样本，必须计入成功率分母。启动故障和数据/环境异常单列保留，不混成控制算法失败。

几何收敛不等于物理三维定位精度；本协议只覆盖静态锁存目标。默认固定参数来自 `config/phase4_static_baseline.yaml`，扰动阶段仅单独覆盖预定因素。

## 运行

在容器 bash 中，确保没有另一个本项目仿真/控制器正在运行。仅源码变化或构建缺失时需要构建：

```bash
cd /root/ur_ws
source /opt/ros/humble/setup.bash
colcon build --packages-select ibvs_ur5 --symlink-install
source install/setup.bash
python3 -m unittest discover -s src/ibvs_ur5/tests -p 'test_*.py'
git diff --check
```

`/tmp/ur5_gazebo.urdf` 必须存在；缺失时按 README 的 xacro 命令生成。

代码检查并本地提交后，执行一轮。输出应位于 Git 工作树外，每轮使用不同目录：

```bash
ros2 run ibvs_ur5 run_phase4_trial.py --output /tmp/phase4_baseline_001
```

完整重启三轮时，后续分别使用 `/tmp/phase4_baseline_002`、`/tmp/phase4_baseline_003`；失败也保留，不覆盖同名目录。不需要手动启动其他节点。每轮自动核对起始关节与 `[0,-1.57,0,-1.57,0,0]` 的最大偏差不超过 0.05 rad，保存原始图像起点，不要求像素逐位相同，也不用有噪声的质心筛掉扰动样本。

默认使用仅服务端模式。上一轮初始化检查发现带 GUI 的启动曾超时；仅服务端方式已经取得位置观测，但 GUI 故障根因尚未确定。

运行器每秒至多查询一次控制器就绪状态，Gazebo 退出时联动结束本轮启动。曾有一轮在控制器服务响应发送失败后崩溃；降低查询频率是减负措施，不代表已经确定或根治底层问题。失败仍保留为启动故障，不计作算法收敛失败。

原手动启动仍默认带 GUI，也可显式使用：

```bash
ros2 launch ibvs_ur5 gazebo_ur5.launch.py gui:=false
```

开发阶段可增加 `--allow-dirty` 做冒烟，版本脏状态会写入结果，不能记为正式干净版本。正式实验先提交工具或配置、再采集；结果最后统一汇总提交。不同 GUI 模式或处理链的结果不得默认为相同条件。

## 读代码时先理解的三个状态

- `first_command`：何时真正开始观察控制过程。
- `hold_start`：当前这一段连续合格区间从何时开始；反弹或数据问题会清空它。
- `end_reason`：为什么结束，区分收敛、控制观察超时、启动超时和执行错误。

先看 `test_trial_metrics.py` 的人工样例，再看 `TrialJudge.observe()`。记录器是对实验作判断，不负责给机器人计算运动速度。AI 辅助代码与实际执行证据应分别说明，能运行不等于已经独立掌握。
